# 점자 입력 공통화 수정본 검증 기록

## 다중 사용자 입장과 휴대폰 요청 경로 수정

점자 입력 말풍선의 세로 padding을 13px에서 8px로, 작성 내용과 상태 표시 사이 여백을 7px에서 3px로 줄였다. 한 줄 작성 중 말풍선 높이가 64px 미만인지 브라우저에서 확인했다.

별도 백엔드 `C:/Users/hi/Desktop/EarLink`에 없던 `/rooms/device` 조회·보고 API를 추가했다. `server/routers/device_presence_router.py`를 생성하고 기존 `room_router.py`에 등록했다. 연결 소유자 토큰, 20초 갱신, 60초 만료, 다른 소유자의 해제 무시를 구현했다. Next.js 코드와 함께 서버를 재시작해야 적용된다. 저장소 내 배포 원본은 `backend/device_presence_router.py`다. 기존 채팅과 동일하게 FastAPI worker 하나를 전제로 한다.

두 번째·세 번째 브라우저는 서버에서 공유된 실제 연결 상태를 읽고 연결 안내·페어링 없이 모드를 선택해 같은 방에 입장했다. 조회 지연·404도 입장을 가리지 않는다. 미연결 안내는 화면을 덮지 않는 선택 사항으로 바꿨다. 프로덕션 검사에서 해제 직후 자신의 이전 연결을 다른 휴대폰의 연결로 오인하는 순서 문제가 발견되어, 해제 보고가 끝난 뒤 조회하도록 수정했다. 해제 보고를 800ms 지연시킨 재검사까지 통과했다.

로컬 환경의 `localhost:8000` 직접 호출은 휴대폰 자신의 서버를 가리킬 수 있었다. HTTP는 `/api/backend` 프록시로, 채팅·수어 WebSocket은 웹 주소의 `/ws` rewrite로 전달하도록 수정했다. 기존 localhost WebSocket 설정도 이 경로를 사용한다. 실제 휴대폰의 오류 화면·네트워크 로그를 확보한 것은 아니므로 기존 오류의 원인을 이것 하나로 확정하지 않는다. 네트워크·백엔드 장애는 재시도 가능한 한국어 오류를 표시한다. 구성은 `.env.example`과 `docs/PRODUCTION_BLUETOOTH.md`에 기록했다.

검증 결과:

- 프로덕션 빌드와 TypeScript 검사 통과.
- 웹 점자·BLE 단위 검사 16개, HTTP·WebSocket 경로 검사 3개 통과.
- 연결 상태 서버 검사 4개와 기존 점자 채팅 서버 검사 7개 통과.
- BLE 브라우저 검사 21개 통과: 선택적 연결 안내, 늦은 조회, API 미설치, 네트워크 실패, 기존 기기 연결·키보드 흐름.
- 실제 HTTP·SQLite·WebSocket으로 브라우저 3개를 연결한 검사 13개 통과. 최종 `next start`에서도 적용된 실제 백엔드 모듈을 사용해 13개 모두 통과.
- 예상하지 않은 브라우저 실행 예외 0건. 360px 폭, 높이 844·667·568px의 기존 채팅 레이아웃 검사 통과.

실제 DB를 사용하지 않는 격리 서버를 사용했고, BLE·음성은 fixture였다. 실물 휴대폰·ESP32 무선 연결은 미검증이며 실서비스 재배포는 하지 않았다. 테스트 서버는 검사 후 종료했다. 아래는 이전 수정의 기록이다.

## 세 모드의 입력 UI와 점자 수신 경로 분리

채팅 화면과 메시지 목록에서 점자 키보드 스냅샷·점역·입력 오류 표시를 제거했다. 기기 중계 훅이 변환한 작성 내용을 다른 참여자의 초안과 함께 수신 말풍선 목록으로 전달한다. 중계 휴대폰에서도 점자 작성 내용과 확정 메시지는 왼쪽에 표시한다.

이번 수정본에서 TypeScript 검사, 웹 점자·BLE 단위 검사 16개, 실제 HTTP·DB·WebSocket을 연결한 다중 브라우저 검사 13개, BLE 브라우저 검사 17개, 프로덕션 빌드가 통과했다. 브라우저 검사는 세 화면에 선택한 모드의 입력 UI 하나만 존재하고, 점자 수신 영역에 입력·전송 컨트롤이 없는지 확인한다. 점자 작성과 전송 중 화면 사용자의 작성 문장 보존, 작성 중 글자 갱신·삭제·확정 전송과 좌우 구분·서버/BLE 재연결도 통과했다. 물리 기기 대신 GATT fixture를 사용했다.

## 점자 사용자를 상대방으로 구분한 후속 수정

화면의 점자 입력창과 웹 전송 버튼을 제거했다. 점자 사용자의 작성 내용과 전송 메시지는 중계 휴대폰에서도 왼쪽에 표시하고, 화면 사용자의 텍스트·수어·음성 메시지는 오른쪽에 표시한다. 작성 중인 글자는 새 말풍선을 누적하지 않고 갱신하며, 삭제·전송·연결 해제를 공유한다. 잠시 입력을 멈춰도 초안은 유지한다.

이번 수정에서 실행한 검사는 웹 점자·BLE 단위 검사 16개, 개발 서버의 브라우저 검사 17개, 실제 HTTP·DB·WebSocket을 사용한 다중 브라우저 검사 13개, 수정한 실제 백엔드 라우터 검사 7개이며 모두 통과했다. TypeScript 검사와 프로덕션 빌드도 통과했다. 브라우저 실행 예외는 0건이었다. BLE와 음성은 fixture를 사용했으며 실제 하드웨어·음성 인식률·카메라 모델 정확도는 검사하지 않았다.

세 모드에서 점자 말풍선의 좌우 구분, 실시간 글자 추가·삭제, 전송 시 초안 제거와 메시지 한 개 추가, 화면 사용자와 점자 사용자가 같은 문장을 보낼 때의 구분, 서버/BLE 재연결, 구 서버 호환을 확인했다. 360×568 수어 화면의 대화 영역은 약 213px이며 가로 넘침은 없었다. 캡처는 `node_modules/.cache/earlink-live-tests/chat-braille-preview.png`에 저장했다. 작성 내용 공유용 서버 변경도 `C:/Users/hi/Desktop/EarLink/server/routers/chat_router.py`에 적용했다.

## 검사 중 발견하여 수정한 문제

1. **이전 음성 인식 세션이 새 녹음을 종료시키는 문제.** 전송 후 새 녹음을 시작한 상태에서 이전 세션의 `onend`가 늦게 도착하면 UI의 녹음 상태가 꺼졌다. 이전 `onerror`도 새 세션에 오류를 표시할 수 있었다. 결과·오류·종료 이벤트를 현재 인식 객체와 비교해 처리하도록 수정했다. 이전 이벤트를 강제로 늦게 발생시키는 브라우저 검사에서 재현 후 수정본 통과를 확인했다.
2. **작은 화면에서 수어 모드의 대화 영역이 좁아지는 문제.** 점자 작성 줄과 카메라를 함께 표시하면 360×568 화면에서 대화 영역이 67px까지 줄었다. 화면 높이 700px 이하에서 카메라 미리보기 높이를 조절했다. 같은 조건의 대화 영역이 약 128px로 늘었고, 360×844·360×667·360×568에서 전송 버튼 표시와 가로 넘침 여부도 통과했다.
3. **기존 수어 코드의 정적 검사 오류 2개.** 자기 자신을 참조하는 재연결 콜백을 이름 있는 함수로 바꾸고, 카메라 초기화가 취소되었는지 먼저 확인한 다음 비동기 초기화 단계에서 상태를 초기화하도록 수정했다. 규칙을 비활성화하지 않고 전체 정적 검사를 통과했다.
4. **정적 검사 도구가 생성된 펌웨어 빌드 환경까지 순회하는 문제.** `.firmware-build/**`를 ESLint의 생성물 제외 목록에 추가했다.

## 새 기능과 기존 기능의 함께 동작 확인

점자 기기를 연결한 참여자가 텍스트·음성·수어 어느 모드를 선택하든 점자 전송이 가능했다. 같은 방의 다른 참여자에게 메시지가 한 번씩 전달되었고, 점자 발신 메시지를 연결 기기로 다시 출력하지 않았다. 기기 전송 키와 웹의 점자 전송 버튼을 모두 검사했다.

미완성 자음을 포함한 점자 작성은 다른 참여자에게 입력 중 말풍선으로 표시되었고, 알림 이벤트가 채팅 메시지·음성 읽기·점자 출력에 섞이지 않았다. 일반 텍스트 입력은 점자 말풍선을 만들지 않았다. 연속 입력 중 상태 갱신, 전체 삭제·전송·연결 해제 시 종료, 유휴 상태와 종료 이벤트 유실 시 만료를 확인했다.

실제 서버 소켓을 종료한 뒤 재연결·기능 재협상·점자 전송 복구까지 확인했다. 방에서 나와 연결 담당자의 모드를 수어로 바꿔도 같은 BLE 연결을 유지했고, 기존 음성·수어 참여자에게 다시 전송할 수 있었다.

## 재현 방법과 결과 파일

기본 검사 명령은 [점자 채팅 API 안내](BRAILLE_CHAT_API.md)에 정리했다. 이번 검사에서는 개발 서버에서 실제 서버 연동 검사를 실행한 뒤, 일반 `.env.local` 설정으로 최종 빌드를 만들고 `next start`에서 17개 브라우저 시나리오를 다시 실행했다. 테스트용 API 주소를 환경변수 파일에 저장하지 않았다.

작업 폴더 내부 결과 파일:

- `node_modules/.cache/earlink-bluetooth-tests/production-report.json`
- `node_modules/.cache/earlink-live-tests/live-report.json`
- `node_modules/.cache/earlink-live-tests/backend-regression.xml`
- `firmware/validation/braille-results.json`

실제 서버 연동 검사는 별도 SQLite 테스트 DB를 사용했다. 기존 수어 서버 검사도 작업 폴더 내부의 별도 SQLite DB로 실행하여 운영 DB를 사용하지 않았다. 테스트용 서버와 브라우저는 검사 후 종료했다.

## 검증 범위의 한계

자동 브라우저 검사의 BLE 입력·출력은 GATT fixture이고, 마이크·음성 합성은 브라우저 API 콜백으로 대체했다. 실제 기기의 무선 품질·버튼 감각·점자 액추에이터 동작·실제 음성 인식률·실시간 카메라 영상에서의 인식 정확도는 검증하지 않았다. TFLite 실제 실행 통과는 모델의 전체 정확도를 보증하는 결과가 아니다. 점역의 UNVERIFIED 13건 역시 미검증 상태를 유지한다.

이번 작업은 로컬 수정본 검증이며 실서비스 재배포는 하지 않았다.
