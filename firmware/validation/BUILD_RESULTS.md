## 현재 돌출점 LOW·배경 HIGH 출력

2026-11-14 추가 변경: 자동 페이지 표시 기본값을 3000ms에서 **2000ms**로 단축했다. 파도 종료 후 1999ms에는 표시를 유지하고 2000ms에 해제하는 경계, 250ms 후 다음 페이지와 큐 전환, 타이머 순환을 기존 검사에서 확인해 통과했다. 연결 파도 200/50ms, 페이지 간격 250ms, 수동 유지 만료 10000ms는 유지했다. 전체 빠른 검사도 다시 통과했다.

2026-11-14, 사용자가 실제 연결 파도에서 HIGH=내려감 / LOW=올라옴을 확인했다. 문자 출력에서 점역 비트 1을 HIGH로 내려 버리던 오류를 수정했다. `DisplayController`가 문자 표시 중에만 돌출 마스크의 하위 6비트를 배경 내림 마스크로 변환한다. 대기·페이지 간격·표시 종료·지우기·연결 해제는 전체 LOW이며, 파도 마스크는 반전하지 않는다. 최종 표시 패턴만 한 번에 래치하므로 전체 HIGH로 미리 내리는 단계가 없다. 표시 중 공백/남는 칸은 실제 배경이므로 HIGH가 된다.

## 이전 선택 출력·BLE 연결 파도 펌웨어

2026-11-13, 전체 HIGH 유지 진단을 종료하고 2024 점역·BLE v1·페이지 처리를 복원했다. 초기화·대기·빈 페이지·지우기·연결 해제는 `00 00 00`으로 해제한다. 점역의 필요한 비트만 해당 물리 채널 HIGH로 연결하고, 사용자 시험과 같은 `data[2]→data[0]` 순서로 전송한다. BLE 연결 때 세로열 3채널씩 200ms, 열 사이 전체 해제 50ms로 왼쪽부터 6열을 알린다. 파도 중 메시지는 수신·변환·큐 등록하고 파도 이후부터 페이지 표시 시간을 계산한다.

## 이전 사용자 검증 코드 기반 전체 신호 유지 스케치

2026-11-13, 사용자가 개별 솔레노이드 시험에 성공한 코드의 핀·역순 전송(`data[2]`부터)·LSBFIRST·시리얼 설정을 바탕으로 전체 신호 유지 코드로 수정했다. 시작 시 하위 6비트가 1인 `3F 3F 3F`를 전송한다. 200ms 후 자동 해제는 없으며, `off`는 사용자 코드와 동일하게 `00 00 00`을 전송한다. `on`/`down`, `status`, `help` 명령을 제공한다. 이전 자동 상태 로그와 리셋 사유 코드는 이 버전에서 제거했다. 점역·BLE·프로젝트 헤더를 사용하지 않는다.

Arduino-ESP32 3.3.12 / `esp32:esp32:esp32` 컴파일 PASS: 플래시 273676바이트 / 정적 RAM 22116바이트. 빌드만 실행했으며 업로드·실물 연속 구동·전압/전류 측정은 하지 않았다. 사용자가 성공을 확인한 것은 제공한 개별 펄스 코드이며, 변경한 18채널 동시 유지 코드의 실제 장치 결과는 아직 **UNVERIFIED**다.

## 이전 단독 전체 내려감 스케치

2026-11-13, 사용자 요청으로 활성 `earlink/earlink.ino`를 프로젝트 헤더·점역·BLE 없이 초기 `3F 3F 3F`를 한 번 전송하고 유지하는 단독 스케치로 교체했다. 전체 기능 원본은 `backups/earlink-full.ino.txt`에 보존했다. GPIO 16/17/18, LSBFIRST, 100ms 초기화 지연을 유지하며 반복 GPIO 전송은 없다. 시리얼에는 리셋 사유와 1초 간격 부팅 후 시간을 기록한다.

Arduino-ESP32 3.3.12 / `esp32:esp32:esp32` 컴파일 PASS: 플래시 272472바이트 / 정적 RAM 22116바이트. `.ino` 하나만 복사한 별도 폴더에서도 동일한 설정으로 컴파일 PASS했으며 크기도 동일했다. 장치 업로드·실물 구동·전압/전류 측정은 하지 않았다. 이 결과는 배터리 정상 여부나 떨림 해결을 검증한 것이 아니다. 아래 전체 기능과 선택 모드 기록은 백업한 전체 펌웨어에 대한 이전 기록이다.

## 재현 명령

프로젝트 루트에서 Python 3.13.7, Node 24.18.0, MSVC C++17로 실행했다. MSVC에는 `/W4 /WX /O2 /utf-8`을 적용했다. g++/clang++ 경로도 스크립트에 있으나 이 환경에서 실행한 것은 MSVC 경로다.

```powershell
python firmware/tests/run_tests.py
node node_modules/typescript/bin/tsc --noEmit --incremental false
arduino-cli compile --fqbn esp32:esp32:esp32 --build-path .firmware-build/esp32 firmware/earlink
python firmware/tools/export_full_code.py
git diff --check
```

Node의 기존 `MODULE_TYPELESS_PACKAGE_JSON` 안내가 출력되지만 5개 테스트는 모두 통과한다. 이 안내를 없애기 위해 웹 프로젝트의 package type을 변경하지 않았다. 프런트엔드 화면·서버·지문자 인식 경로는 수정하지 않았다.

`braille-results.json`에는 각 입력의 예상/실제 점자·칸 수·점 번호·6비트 마스크·각 칸의 적용 규칙·원문 위치가 있다. `code-manifest.json`은 FULL_CODE.md에 수록된 실제 코드 파일 24개의 **LF 정규화 SHA-256**을 기록한다. `official-source-audit.json`은 공식 PDF 글꼴 대조 기록이다. [전수·장시간 검증 상세](DEEP_VALIDATION.md)에 반복 수와 발견한 오류를 기록했다.

## 해석할 때 주의할 제한

PASS는 고정된 입력과 근거 조항을 대조했다는 뜻이다. `manual-rule-composition`은 실제 원문 문장과 직접 대조한 결과가 아니라 공식 조항으로 직접 작성한 기대값과의 일치다. 미지원 항목·애플리케이션 표시 정책은 UNVERIFIED로 유지했다.

펌웨어가 미지원·미검증 규칙으로 진단하는 입력은 기존 BAD_PACKET으로 메시지 전체를 거부한다. UNVERIFIED 중 표시 정책/NFD/원시 셀은 동작을 지원하지만 규정 직접 대조 PASS로 분류하지 않은 경우다. 테스트 판정과 실제 지원 여부를 동일하게 해석하면 안 된다.
